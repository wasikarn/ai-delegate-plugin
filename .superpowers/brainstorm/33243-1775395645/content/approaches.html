Path D — 3 Approaches

เลือก architecture สำหรับ peer debate round

A

Shared Context Injection

ส่งผลของ expert อื่นเป็น context ก่อน debate call

หลัง Path B analysis → รวบรวม disputed findings → เรียก expert แต่ละคนอีกครั้ง พร้อม inject findings ของ peers เป็น system context → expert ตอบสนองด้วย structured JSON

Mechanism: BackendClient call ปกติ (Path A SDK) ไม่ใช้ Agent Teams จริงๆ แค่เลียนแบบ "เห็นงานกัน"

Pros

  • ง่าย implement มาก
  • Cost ต่ำ (kimi x N calls)
  • No experimental API

Cons

  • ไม่ใช่ "real" peer debate
  • Experts ไม่ back-and-forth กัน
  • Context injection ≠ true messaging
B

Agent Teams (True P2P) ⭐ Recommended

ใช้ Claude Code Agent Teams จริงๆ — experts ส่ง message ถึงกันโดยตรง

Lead agent สร้าง team ของ expert teammates → แชร์ disputed findings ผ่าน shared task list → experts ส่ง message โดยตรงผ่าน mailbox → 1 debate round → lead collect responses → Adjudicator synthesize unresolved
Models: Experts = kimi-k2.5:cloud · Lead = Sonnet (already enabled in settings)

Pros

  • True peer visibility
  • Experts challenge กันจริง
  • Article validates approach
  • User already has feature enabled

Cons

  • Experimental API (no session resumption)
  • Higher token cost (~4-5x debate round)
  • More complex orchestration
C

Async Message Bus (File-Based)

experts เขียน/อ่าน findings จาก shared file แทน Agent Teams mailbox

ใช้ temp directory เป็น "message bus" — expert A เขียน findings → expert B อ่าน + respond → collect ทั้งหมด → Adjudicator ตัดสิน ไม่ต้องพึ่ง experimental Agent Teams API

Pros

  • ไม่พึ่ง experimental feature
  • Stable, testable
  • Works with any CLI path (A/B/C)

Cons

  • Sequential (B ต้องรอ A เสร็จก่อน)
  • File I/O overhead
  • ไม่ใช่ true P2P
Recommendation: B — ใช้ Agent Teams จริง เพราะ user มี experimental feature เปิดอยู่แล้ว และ article validate approach นี้โดยตรง Approach A เลียนแบบ debate แต่ไม่ใช่ของจริง Approach C ยังดีแต่ sequential ไม่ใช่ P2P
